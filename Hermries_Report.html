Assessment

The sample presents itself as a link-safety utility, but also implements a way to make a supplied search provider Chrome’s default. The feature goes beyond opening a reputation site for one URL: it can affect future address-bar searches. The best-supported working assessment is a potentially unwanted application with search-steering capability, not an anti-debugger or a confirmed malware family.

What is measured: frontend logic for completing onboarding and handling an offer, a native configuration command, and native references to automating the browser UI. What is inferred: a commercial motive for steering searches is plausible, but no payment arrangement, operator, or ultimate provider was identified. Consent is an investigative question, not a conclusion drawn from a toggle.

Operational decision: hunt for the executable using R08, corroborate application identity with R05, then look for a change in the affected browser profile. Use R03 for a raw, compressed package. Do not block shared services, a loader DLL, or a publisher based on these findings.

Evidence from the executable

  1. Link-checking is more than branding. The embedded UI describes reputation providers and includes a VirusTotal domain-lookup URL template. These are links to safety services, not evidence those services control the application.
  2. The welcome timer saves preferences; it does not directly change Chrome. In the decoded frontend the defaults for showMoreOffers, dsSync and enableAnalytics are true. A 30-second countdown calls the same completion routine as “Get Started,” submitting the current preferences to complete_welcome. See decoded JS offsets 0x3be96 and 0x3bfc1.
  3. The offer action is the important link. At decoded JS offsets 0x3d4e5 and 0x3d519, a notification action named apply_config needs a searchEngine object. The path checks both DsSync and ShowMoreOffers before invoking the wrapper for sdk_apply_profile_config (command at JS offset 0x230a). This shows a route from an interaction to configuration, not proof a real offer arrived or was accepted.
  4. Native code implements the relevant UI operation. An instruction at RVA 0x26c15e references the message [chrome] 'Make default' found, clicking at PE file offset 0x6e3d55. The same function references the alternative where the option is absent. Another message concerns killing existing Chrome processes for a fresh launch—not terminating security software.
  5. Input changes automation timing. Native instructions at RVAs 0x26527a and 0x2666da in one function reference waiting for idle time and interruption by user activity. Elsewhere, verified call sites resolve to GetLastInputInfo and SendInput. This could reduce disruption or visibility; it is not proof of an anti-sandbox decision.

Three offset spaces: ZIP offsets refer to bytes in the original archive. PE offsets refer to the uncompressed EXE on disk; RVAs are addresses relative to image base 0x140000000. The frontend is a Brotli asset at PE offset 0x6a47fb: 81,814 compressed bytes decode in memory to 272,043 bytes of JavaScript. JS offsets refer only to that decoded text, which was not executed.

Package structure, PE hardening and integrity evidence

ZIP-based Windows application package, 56 members: executable, WebView2 loader, 49 PNG assets, three XML documents, a code-integrity catalog and a package signature. Each supplied extracted file matched the bytes of its archive member. The manifest declares Windows.FullTrustApplication, runFullTrust and internetClient; full trust is not proof of administrator rights or network use.

The native PE32+ AMD64 GUI image has 11 sections, entry RVA 0x13e0, two TLS callbacks, a stripped debug directory, ASLR and NX-compatible flags, no writable-and-executable section, no trailing overlay and no embedded PE certificate table. Rust module names and Tauri resources survive stripping. The archive contains separate signing artifacts. Neither signer trust nor signature-chain validity was established.

Three package-signature tag payloads corresponded to independently calculated digests: AXCT for [Content_Types].xml, AXBM for AppxBlockMap.xml and AXCI for the catalog. The catalog includes the UTF-16LE full package name. These cross-links support build consistency, not authenticity or safety. The block map’s 142 EXE blocks and its separate FileHash agreed with the actual executable.

Generic imports such as VirtualProtect, GetProcAddress and TerminateProcess do not identify evasion. A targeted case-insensitive ASCII/UTF-16LE check found no literal IsDebuggerPresent, NtQueryInformationProcess, AmsiScanBuffer, WinDefend, MsMpEng or VBoxService.exe. Encoded strings, dynamic resolution and unreviewed code limit this negative evidence.

What is worth checking next?

  1. Did a provider change, and to what? Preserve timestamped browser-profile settings, search-provider history/backups and applicable enterprise policy. Compare prior and current provider name, search URL template and redirect parameters. Tie the affected profile and user to process lifetime and browser restart records. A changed setting by itself does not identify the actor.
  2. What authorized the change? Look for an offer or notification record, action name, proposed provider, saved preferences and timestamps. Compare what the user was shown with what was applied. The presence of an enabled flag, an expired onboarding timer, or an analytics label is not proof of informed consent.
  3. Was the program present or active? First locate the exact package or PE hash; then use existing process-start, package-inventory and startup activation records for the same host/account. Distinguish installed, registered, launched and actually changed settings. Review available EDR process lineage around browser restarts and any PowerShell activity; do not assume a particular Windows event source was enabled.
  4. Were destinations contacted? Use existing endpoint/proxy/DNS records, time and process attribution where available. Distinguish an intentional reputation-site visit from configuration delivery, telemetry, or the final provider. ISP flow data alone cannot establish a local preference change, and shared IPs are weak indicators.
  5. Will the rule hold up? Compare unrelated benign Tauri/WebView2 applications, authorized builds of this app, and ordinary APPX manifests. Validate code signing and deployment provenance separately. Keep R08 as a hunt until the false-positive and variant evidence supports a stronger action.
